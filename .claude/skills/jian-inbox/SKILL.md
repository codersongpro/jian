# 지안 작품 수신함 반영

가족이 드라이브 수신함에 올린 사진을 전시 작품으로 바꿔 **PR까지만** 만든다. 공개는 사용자가 PR을 병합해야 이루어진다. 직접 main에 푸시하지 않는다.

## 고정 정보

| 항목 | 값 |
| --- | --- |
| 수신함 폴더 | `1GuDjTa-1lJQDNlxpdgtpz2G4eCQvHmO-` (지안 작품 수신함) |
| 반영 완료 폴더 | `1dcn4RSPK9wW0niRqGyIpC4Rqc1BIMTmo` (수신함 안 「반영 완료」) |
| 원본 보관 폴더 | 수신함 안 「원본 보관」. 큰 사진 자동 줄이기 스크립트가 원본을 옮겨 두는 곳. 처리 대상 아님 |
| 큰 사진 자동 줄이기 | Google Apps Script `scripts/drive-inbox-resizer/` (설치 안내 `docs/drive-inbox-resizer.md`) |
| 사용 안내 문서 | 수신함 안 「📌 사용 안내」 Google 문서. 처리 대상 아님 |
| 이미지 변환 | `python3 -I scripts/inbox_photo.py <입력> <본문.jpg> [--thumb <썸네일.webp>]` (ImageMagick 필요) |

Google Drive 커넥터가 필요하다. 연결되어 있지 않으면 사용자에게 claude.ai 커넥터 설정에서 Google Drive를 연결해 달라고 하고 멈춘다.

## 1. 수신함 읽기

1. `search_files`로 `parentId = '<수신함>'`을 조회한다. `반영 완료`·`원본 보관` 폴더와 사용 안내 문서는 건너뛴다.
   - 설명(description)이 `jian-resize v1 `로 시작하는 파일은 Apps Script가 큰 사진을 줄인 사본이다. 설명의 JSON에 원래 업로드 시각(`uploaded`)과 촬영 정보가 있다.
   - **4.5MB가 넘는 이미지**는 Drive 커넥터로 받을 수 없다(약 5MB 한도). 내려받지 말고 수신함에 둔다. Apps Script가 5분마다 확인해, 마지막 업로드 뒤 5분이 지나면 줄인 사본으로 바꾼다. 보고에 「업로드 뒤 5~10분 안에 자동으로 줄어듦. 기다리기 싫으면 「지금 줄이기」 웹앱 주소를 열기」라고 적고, 사용자가 원하면 15분쯤 뒤 다시 확인한다. 업로드한 지 30분이 지나도 그대로면 스크립트가 멈춘 것이니 사용자에게 트리거(`checkInbox`)·실행 기록을 확인해 달라고 한다.
2. 묶음 규칙
   - **하위 폴더 1개 = 작품 1개.** 폴더 이름이 한 줄 메모다. 폴더 안 이미지들을 `parentId = '<폴더>'`로 조회해 `createdTime` 오름차순(먼저 올린 사진이 대표)으로 정렬한다. 줄인 사본은 설명의 `uploaded`를 `createdTime` 대신 쓴다.
   - **폴더 밖 낱장 사진 1장 = 작품 1개.** 확장자를 뺀 파일 이름이 메모다. 단, `IMG_1234`, `20261018_153000`, `PXL_…`, UUID처럼 카메라가 붙인 이름이면 메모 없음으로 본다.
   - 메모 없는 낱장 사진은 사진을 보고 묶는다. 같은 작품을 다른 각도나 부분으로 찍은 것이 분명하고(같은 종이·대상·색) 올린 시각이 가까우면 작품 1개로 합친다. 애매하면 나누고 PR에 적는다.
   - 이미지가 아닌 파일(영상·문서)은 처리하지 않고 결과 보고에 적는다.
3. 아무것도 없으면 "수신함이 비어 있습니다"라고 알리고 끝낸다.
4. 처리 목록(작품별 메모, 사진 수)을 사용자에게 한 줄씩 먼저 보여 주고 진행한다.

## 2. 브랜치

- `git fetch origin main` 후 **origin/main에서** 작업 브랜치를 만든다. 세션에 지정된 작업 브랜치가 있으면 그 이름을, 없으면 `inbox/YYYY-MM-DD`를 쓴다.
- 작업 브랜치에 이미 병합된 이전 반영분만 있으면 origin/main으로 다시 시작한다.

## 3. 사진 받기와 변환

- `download_file_content(fileId)`로 받는다. 큰 사진은 결과가 파일로 저장되었다는 안내와 경로가 나오므로 **그 JSON 경로를 그대로** 스크립트 입력으로 넘긴다. 작은 사진이 본문에 바로 나오면 그 JSON을 스크래치패드에 저장해서 넘긴다. base64를 대화에 옮겨 적지 않는다.
- 줄인 사본(설명이 `jian-resize v1 `로 시작)은 스크립트에 `--meta '<설명 전체>'`를 붙인다. 사본에는 EXIF가 없어서, 설명에 적힌 촬영 시각·좌표로 날짜와 시·군을 구한다(출력 `date_source`: `drive`).
- 작품 id는 영문 소문자·숫자·하이픈 슬러그로 정한다(예: `fall-tree`). `content/works.json`의 기존 id와 겹치지 않게 한다.
- 파일 위치: 본문 `public/works/<id>/page-01.jpg`, `page-02.jpg` …, 대표 사진만 `--thumb public/works/thumbnails/<id>.webp`.
- 스크립트가 촬영 날짜·시간 읽기, 촬영 위치를 **시·군 이름으로 변환**(`scripts/data/korea-sigun.json`, 오프라인), 회전 보정, **정확한 GPS 좌표·기기 정보 제거**, 크기 축소(본문 긴 변 1536px, 썸네일 640px)를 한다. 출력 JSON의 `date`, `time`, `place`, `place_en`을 기록해 둔다.
- 위치는 **시·군 단위까지만** 공개한다(사용자 결정, 2026-10-19). 좌표나 읍·면·동, 구 이름은 어디에도 적지 않는다.
- 변환이 끝나면 저장된 도구 결과 파일(원본 base64)은 지운다.

## 4. 사진 확인 (공개 전 안전 점검)

변환된 `page-*.jpg`를 Read로 직접 본다. 다음이 보이면 **그 작품은 반영하지 않고** 보고에 이유를 적는다. 사용자가 허락하면 잘라내거나 가려서 다시 처리한다.

- 아이 얼굴, 다른 사람 얼굴
- 실명(지안 외), 학교 이름, 반·번호, 주소, 전화번호, 차량 번호
- 다른 사람이 만든 작품이나 책·인쇄물을 그대로 찍은 사진

**학원 이름이나 상표**(공책·교재에 인쇄된 학원명, 제품 로고 등)는 제외 사유가 아니다. 그대로 반영한다(사용자 결정, 2026-10-19).

## 5. 내용 작성

### 카테고리
`lib/model.ts`의 `categories`(「전체」 제외) 중 하나만 고른다: 문학, 과학, 수학, 음악, 미술, 발레, 그림책, 공예·디자인, 사회·기획, 앱 기획, 공부 기록, 체험·활동.
- 그림이 중심이면 미술, 이야기가 있는 여러 쪽 그림이면 그림책, 입체·만들기는 공예·디자인, 공책·문제 풀이는 공부 기록이나 수학으로 본다.
- 애매하면 메모를 우선하고, PR 본문에 다른 후보를 함께 적는다.

### 메모가 없을 때 (사진만 올린 경우)
가족이 설명 없이 사진만 올리는 것이 기본이라고 보고, **사진 분석만으로 모두 작성한다.** 메모를 요청하며 멈추지 않는다.
- **제목**: 사진 속에 지안이 쓴 제목이 있으면 그대로 쓴다. 없으면 보이는 대상을 담아 짧게 짓는다(예: `노란 우산을 쓴 고양이`).
- **카테고리**: 재료·형식·내용으로 고른다(아래 기준).
- **소개**: 무엇을, 어떤 재료와 방식으로 표현했는지 사진에서 확인되는 것만 쓴다(예: `크레파스로 칠한 바다 위에 오려 붙인 종이배를 띄운 그림.`).
- **본문**: 사진 속 글씨가 있으면 전사한다. 없으면 소개 문장과 "원본 사진으로 감상해 주세요."를 쓴다.
- 장소·함께한 사람·만든 기간·동기는 사진으로 알 수 없으므로 쓰지 않는다.
- `authorship_note`: `보호자가 수신함에 올린 사진. 메모 없음, 제목·소개는 사진 분석으로 작성`
- PR 표의 메모 칸에 `없음 (사진 분석)`이라고 적어, 사용자가 확인할 때 Claude가 지은 제목임을 알 수 있게 한다.

### 사실과 표현 구분
- **사실**(날짜, 장소, 혼자/함께, 만든 기간, 지안이 한 말)은 **메모와 사진에 보이는 것만** 쓴다. 추정하지 않는다.
- **표현**(제목이 없을 때의 제목, 소개 문장, 영어 번역)은 Claude가 쓴다.
- 사진 속 글씨는 보이는 그대로 옮기고, 읽을 수 없는 부분은 `[판독 불가]`로 둔다. 맞춤법을 고치지 않는다.
- 칭찬·평가(“뛰어난”, “천재적인”)와 감정 추측(“즐겁게 그렸다”)은 쓰지 않는다.

### works.json 항목
기존 항목과 같은 형태로 **배열 끝에** 추가한다.

```json
{
  "id": "fall-tree",
  "title": "가을 나무",
  "title_en": "Autumn Tree",
  "category": "미술",
  "year": 2026,
  "description": "노랑·주황 잎이 떨어지는 큰 나무를 색연필로 그린 그림.",
  "description_en": "A big tree dropping yellow and orange leaves, drawn in colored pencil.",
  "content_file": "fall-tree.md",
  "is_public": true,
  "featured_order": null,
  "motion_enabled": true,
  "youtube_id": null,
  "thumbnail_url": "/works/thumbnails/fall-tree.webp",
  "pages": [{ "url": "/works/fall-tree/page-01.jpg", "caption": "전체 그림" }],
  "provenance": {
    "category": "미술",
    "date": "2026-10-18",
    "date_basis": "사진 촬영일(EXIF). 실제 완성일과 다를 수 있음",
    "creator_display": "Jian",
    "evidence_level": "실제 파일 육안 확인",
    "authorship_note": "보호자가 수신함에 올린 사진. 메모: “가을 나무 - 학교 미술 시간에 그림”",
    "photo_taken": "2026-10-18 15:30",
    "photo_place": "경기도 성남시",
    "photo_place_en": "Seongnam-si, Gyeonggi-do"
  }
}
```

- `description`은 한 문장이고 명사형으로 끝낸다(기존 항목 문체). 무엇을 어떤 재료로 만들었는지 쓴다.
- 날짜 우선순위
  1. 메모에 만든 때가 있으면 그것을 쓴다. `date_basis`: `보호자 메모` (월까지만 있으면 `date`는 `null`, `year`만 채운다)
  2. 없으면 촬영일(EXIF). `date_basis`: `사진 촬영일(EXIF). 실제 완성일과 다를 수 있음`. 줄인 사본에서 `date_source`가 `drive`이면 `사진 촬영일(드라이브 기록). 실제 완성일과 다를 수 있음`
  3. 촬영일 정보가 없으면 Drive `createdTime`의 날짜(한국 시간). `date_basis`: `Drive 업로드일(사진에 촬영일 정보 없음)`
  - `year`는 정해진 날짜의 연도다.
- `photo_taken`은 대표 사진의 스크립트 출력 `date`와 `time`을 합친 값이다. `photo_place`·`photo_place_en`은 `place`·`place_en`이다. 값이 없으면(촬영 정보 없음, 국외) 그 필드를 넣지 않는다. 작품 상세 창의 「사진 촬영」 줄에 표시된다.
- 캡션은 사진마다 무엇이 보이는지 짧게 쓴다(예: `전체 그림`, `뒷면`, `세부: 날개`).
- `featured_order`는 항상 `null`이다. 대표 작품 지정은 사용자가 한다.

### 본문 md (`content/<id>.md`)
기존 사진 작품(`content/brain-journey.md`, `content/acorn.md`)처럼 짧게 쓴다.

```markdown
# 가을 나무

노랑·주황 잎이 떨어지는 큰 나무를 색연필로 그린 그림. 원본 사진으로 감상해 주세요.
```

사진에 글이 있으면 제목 아래에 전사를 덧붙인다.

## 6. 검증

```bash
npm test
npm run typecheck
npm run build
```

테스트의 작품 수는 `tests/expected.ts`가 `works.json`에서 계산하므로 고칠 필요가 없다. 실패하면 원인을 고친 뒤 다시 실행한다. 테스트를 건너뛰거나 지우지 않는다.

## 7. PR

- 커밋 메시지: `content: add N works from the family inbox`
- main 대상 PR을 만든다. 제목: `수신함 작품 N개 추가 (YYYY-MM-DD)`
- 본문 표: `작품 | 카테고리(다른 후보) | 날짜와 근거 | 메모 원문 | 사진 수`
- 이어서 다음을 적는다.
  - 제외한 사진과 이유(안전 점검, 형식)
  - Claude가 추정한 부분(제목을 지었는지, 카테고리가 애매했는지)
  - "병합하면 Vercel이 배포해 사이트에 공개됩니다. 수정할 내용은 이 PR에 댓글로 남기거나 대화로 알려 주세요."
- **PR을 만든 뒤에만** 처리한 사진과 폴더를 `update_file(parentId=<반영 완료>)`로 옮긴다. 안전 점검으로 제외한 사진은 수신함에 남긴다. 줄인 사본도 똑같이 옮기고, 「원본 보관」의 원본은 건드리지 않는다.

## 8. 사용자에게 보고

PR 링크, 반영한 작품 목록(제목·카테고리), 제외한 사진, 확인이 필요한 점을 짧게 알린다. 병합은 사용자가 결정한다.
